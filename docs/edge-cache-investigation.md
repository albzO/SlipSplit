# 清缓存后自动框变化：只读调查

用户已确认重新构建安装，并允许只读取 App 的图片、日志及版本信息。
本轮没有点击或切换手机界面，没有安装、清缓存、停止进程或运行设备测试。

## 已确认

- 手机上的 `base.apk` 与本机 `app/build/intermediates/apk/debug/app-debug.apk` SHA256 相同：
  `d3a2555b3861337a33b0d40e59539d2cd3c603c2a82d721701dfa44e063a2cd2`。
  不能再用“未安装新版本”解释用户反馈。
- 当前 `code_cache` 未发现覆盖 DEX 文件。这不证明此前从未有过增量部署缓存。
- 评分权重、门槛及候选算法编译在 Kotlin 代码里，没有从缓存文件读取评分配置。
- `cache/photos` 存的是导入图片及确认后的处理图。四角还可由 Activity 的 savedInstanceState 恢复。
  先前只要恢复出有效四角，就跳过自动检测；因此恢复的好框不能当作新算法成功运行的证据。

## 读取到的实际输入

只读取了 App 当前三次导入的 `source.image`：

- 前两次文件 SHA256 相同，均为 3072×4096、带木桌的原照片；ICC 为 Display P3。
- 最近一次是另一份 1777×4000 的高对比、已经裁剪后的扫描图，不能与带桌面的原片混作同一输入比较。
- 最新日志对应最近一次导入：`import_ms=11`、`preview_ms=36`、`edges_ms=21`、`found=false`。
  没有相关 OpenCV 加载异常。该图的纸张已经接近占满整张图片，没有桌面边界，返回整图并不代表评分被删除。
  这些耗时不能代替前两次原片的耗时，已有日志不足以还原它们当时的最终四角。

原始诊断文件仅保存在本机被忽略的 `logs/phone-readonly/`。
电脑上对读取到的带桌面原片运行同规则重放，能找到小票候选；
但电脑 OpenCV 版本、解码与 Android 的完整路径仍有差异，不能据此宣称手机故障已修复。

## 已作的代码调整

- 只有用户手动调整／重置的四角才在页面恢复时直接保留。
  自动生成的四角在新 Activity 中重新计算，避免旧框被误认为新检测结果。
- 增加检测版本号、Debug 输入 SHA256、预览尺寸、色彩空间、运行模式和实际四角日志。
  后续可用同一输入指纹比较清缓存前后，区分输入变化、状态恢复和算法结果。
- 保留手机只读约定：没有替用户安装包含这些新增诊断的 APK，代码更改尚未做设备验证。

目前没有充分证据将用户观察到的全部变化归因于缓存恢复，不能把本轮调整表述为找边准确率已经修复。
